## What DOT has today (verified in code/database)
- **Identity:** Lovable Cloud auth (email/password, Google, OTP). `auth.users.id` (uuid) is the primary key; `profiles.id` = same uuid; public handle `profiles.dot_id` (unique, generated by `generate_dot_id()`); `profiles.username`, `verified`, `suspended`. Roles in `user_roles` (app_role enum incl. founder, community_leader, admin, super_admin, moderator…), checked via `has_role` / `is_admin` / `is_active_member`.
- **OAuth server already enabled** on DOT's auth (added for the MCP integration, `src/lib/mcp/supabase.ts`). This is the cleanest way for Ping to "Sign in with DOT".
- **Communities:** `communities` (id, name, description, leader_id, community_type, university_name, city, country, region, visibility, referral_code) and `community_members` (community_id, founder_id, status). Writes only via `join_community`, `join_community_by_code`, `leave_community` RPCs; reads via `list_communities`; wrapped in `src/lib/communities.functions.ts`; UI at `/explore-communities`, `/explore-communities/$id`, `/community`, `/join/$code`.
- **Challenge:** `challenge_checkins.ping_update_url` and `enrollments.ping_profile_url` — plain participant-pasted links only, via `save_challenge_progress`. No real Ping link.
- **Pitchathons, Academy/AVA, admin:** no Ping references. Admin audit tables exist (`admin_audit_log`, `role_audit_log`).
- **Server endpoints:** only one public route (`/api/public/webhooks/paystack` — out of scope, not touched). No Ping endpoint, no Ping secret, no outbound calls, no CORS config.
- **Not implemented:** identity linking, hub sync, DM launch, notifications, deep links, webhooks to/from Ping.

## Integration principles
1. **Ping owns all messaging and groups.** DOT stores only link IDs and sync status — no messages, no second group system.
2. **DOT owns identity, communities and roles** (source of truth); Ping mirrors.
3. Link by stable uuid, never by email or display name.
4. All server-to-server traffic signed; no secrets in the browser.

## Proposed design

### 1. Identity linking
- Preferred: Ping uses **"Sign in with DOT"** through DOT's existing OAuth server. Ping receives DOT `sub` (user uuid) + `dot_id`; stores it as its external identity.
- Fallback if Ping has separate accounts: signed-in DOT user clicks "Connect Ping" → redirected to Ping with a short-lived signed `state` → Ping confirms → calls DOT callback → link saved.
- New DOT table `ping_identity_links` (user_id uuid unique, ping_user_id text unique, linked_at, unlinked_at, status). Owner can read own row; only server writes. Unlink supported.
- Mismatch to check in Phase 0: if Ping runs its own auth on a separate backend, user uuids will differ — the link table is mandatory.

### 2. DOT community → Ping hub mapping
New table `ping_hub_links` (community_id unique, ping_hub_id unique, sync_status, last_synced_at, last_error). Field mapping: name, description, community_type, university_name/city/country/region, visibility (public/invite_only → Ping visibility), leader → hub owner. Created only when leader/admin clicks "Create Ping hub". No fake counts.

### 3. Membership and roles
- Existing join/leave RPCs stay the only write path. After a successful join/leave, enqueue an outbound event (outbox table `ping_outbox`: id, event_type, payload, idempotency_key unique, attempts, next_attempt_at, status).
- Role mapping: community leader → hub owner; DOT admin/moderator → hub moderator only if Ping supports it; members → member. Unlinked users are skipped and retried after they link.

### 4. Direct messages and notifications
- "Message on Ping" button on founder profiles and community member lists = **deep link** (e.g. `ping://dm?dot_id=…` / `https://<ping>/dm/<ping_user_id>`), shown only when both users are linked. DOT never sends message content.
- Notifications: Ping keeps its own. DOT sends only event notices (joined hub, challenge milestone reviewed, Pitchathon status) if Ping exposes an endpoint.

### 5. Deep links
Ping → DOT: `/founder/$dotId`, `/explore-communities/$id`, `/challenge`, `/pitchathons`, `/academy`. DOT → Ping: hub and DM links built from stored IDs; the base URL is a setting, not hard-coded.

### 6. Endpoints (DOT side)
- `POST /api/public/ping/webhook` — Ping → DOT events (link confirmed, hub created, member left in Ping). HMAC-SHA256 over raw body + timestamp header, 5-min window, timing-safe compare, Zod validation, event-id dedupe table `ping_webhook_events`.
- `POST /api/public/ping/link/callback` — completes account linking (validates signed state).
- Server functions (signed-in): `startPingLink`, `unlinkPing`, `getPingStatus`, `createPingHub` (leader/admin checked server-side), `getPingDeepLink`.
- Outbox worker: `POST /api/public/ping/dispatch` called by a schedule with a shared secret; retries with backoff, max attempts, dead-letter status visible to admins.
- Ping side endpoints (hub create/update, member add/remove, user resolve): **must be verified or built in Ping**.

### 7. Security
- Secrets (names only): `PING_API_BASE_URL`, `PING_API_KEY` (DOT→Ping), `PING_WEBHOOK_SECRET` (Ping→DOT), `PING_LINK_STATE_SECRET`, `PING_DISPATCH_SECRET`. Stored in project secrets; read only inside server handlers.
- CORS: none needed (server-to-server); webhook routes reject browser origins.
- RLS: new tables locked; owner-only read of own link; admin read of sync status; writes only via security-definer functions/server.
- Rate limits: per-user cap on link attempts and hub creation; webhook dedupe.
- Audit: link/unlink, hub create, role sync and failures written to `admin_audit_log`. Admin "Ping sync" panel in the existing admin page.

### 8. Tests
Webhook signature valid/invalid/expired/replayed; duplicate event ignored; link state tamper/expiry; unlinked user skipped; join/leave enqueues exactly one event; invite-only respected; non-leader cannot create hub; outbox retry and dead-letter; no message content stored in DOT.

### 9. Rollout

2. Hub creation + membership sync for one pilot community.
3. DM deep links + event notices.
4. Open to all members; monitor admin sync panel.
